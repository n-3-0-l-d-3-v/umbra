Merge Sort, Taken Apart: Why Cutting the Problem in Half Keeps Paying Off

Picture sixty answer scripts that need to go back to students in register-number order, dumped on a desk in no particular order. Sorting them alone, one sheet at a time, is painful. What works much better is splitting the pile with a friend, each of you sorting one half, and then putting the two sorted stacks side by side and repeatedly picking whichever top sheet has the smaller number.

That last step is the whole idea behind merge sort. If you already have two sorted stacks, combining them is easy and fast. The clever part is realising you can keep splitting until every "stack" is a single sheet, which is sorted by definition, and then build everything back up with that same easy merge.

In this post I go through how merge sort works, trace it by hand on a real example, prove its running time two different ways, and then check the theory against actual measurements from my own code. At the end there is a link to a browser game I built where you make every one of merge sort's decisions yourself.

1. The idea: divide and conquer

Merge sort is the textbook example of the divide and conquer strategy, which has three parts:

  1. Divide the array into two halves at the middle index.
  2. Conquer each half by sorting it recursively with merge sort.
  3. Combine the two sorted halves into one sorted array using a merge.

The recursion stops when a piece has zero or one element, because such a piece is already sorted. Notice where the real work happens. In quicksort, the hard work is done before recursing (partitioning). In merge sort, dividing is trivial (just compute the midpoint) and all the work is done after recursing, in the merge.

2. Pseudocode

MERGE-SORT(A, l, r)
    if l >= r:                     // 0 or 1 element: already sorted
        return
    m = floor((l + r) / 2)
    MERGE-SORT(A, l, m)            // sort left half
    MERGE-SORT(A, m + 1, r)        // sort right half
    MERGE(A, l, m, r)              // combine

MERGE(A, l, m, r)
    L = copy of A[l..m]
    R = copy of A[m+1..r]
    i = 0, j = 0, k = l
    while i < len(L) and j < len(R):
        if L[i] <= R[j]:
            A[k] = L[i];  i = i + 1
        else:
            A[k] = R[j];  j = j + 1
        k = k + 1
    copy any remaining elements of L, then of R, into A[k..r]

The initial call is MERGE-SORT(A, 0, n-1).

Two details matter more than they look:

  • <= and not <. When L[i] and R[j] are equal, we take the one from the left half first. Since everything in the left half came earlier in the original array, equal elements keep their original order. That property is called stability, and it is the reason merge sort is the go-to algorithm when you sort records by one field after already sorting them by another (for example, sort students by name, then stable-sort by marks, and students with the same marks stay in alphabetical order).
  • The leftover copy needs no comparisons. Once one half runs out, whatever remains in the other half is already sorted and larger than everything placed so far, so it is copied straight across.

3. Working through an example

Let us sort this array of eight numbers:

A = [42, 17, 8, 93, 25, 61, 4, 50]

Divide phase

The midpoint of indices 0..7 is 3, so we split into [42, 17, 8, 93] and [25, 61, 4, 50]. Each of those splits again, and again, until we are left with eight single-element pieces. The top half of the figure below shows this. No comparisons have been made yet; dividing only computes indices.

Merge phase

Now we climb back up.

Level 1 (pairs). Each pair of singletons needs exactly one comparison: [42] + [17] → [17, 42], [8] + [93] → [8, 93], [25] + [61] → [25, 61], [4] + [50] → [4, 50]. That is 4 comparisons.

Level 2 (fours). Merging [17, 42] with [8, 93]:

Three comparisons. The right side, [25, 61] + [4, 50], also takes three and gives [4, 25, 50, 61]. Level total: 6 comparisons.

Level 3 (the final merge). [8, 17, 42, 93] with [4, 25, 50, 61]:

Seven comparisons, and the array is sorted.

Total: 4 + 6 + 7 = 17 comparisons for 8 elements. For comparison, n log₂ n = 8 × 3 = 24, and a quadratic algorithm could need up to n(n−1)/2 = 28. If you load this exact array into the simulator described in Section 10, the counter at the end reads 17, which is a nice sanity check that the hand trace and the code agree.

A useful rule falls out of the tables: merging two sorted lists with a total of k elements takes at most k − 1 comparisons. Every comparison places one element, and the last element is always placed for free.

4. Time complexity

Setting up the recurrence

Let T(n) be the time to merge sort n elements. Dividing takes constant time, the two recursive calls take T(n/2) each, and merging n elements takes at most cn time. So:

T(n) = 2·T(n/2) + cn      for n > 1
T(1) = c

Method 1: the recursion tree

Draw each call as a node labelled with the non-recursive work it does.

  • The root does cn work.
  • Level 1 has 2 nodes doing cn/2 each: total cn.
  • Level 2 has 4 nodes doing cn/4 each: total cn.
  • In general, level d has 2ᵈ nodes each doing cn/2ᵈ, which is still cn per level.

The problem size halves at each level, so it reaches 1 after log₂n halvings, giving log₂n + 1 levels. Therefore:

T(n) = cn · (log₂n + 1) = cn·log₂n + cn = Θ(n log n)

This picture is worth remembering because it explains why merge sort is n log n: the work per level never shrinks (you always touch all n elements), but the number of levels is only logarithmic.

Method 2: the Master Theorem

The recurrence has the form T(n) = a·T(n/b) + f(n) with a = 2, b = 2, f(n) = Θ(n). Compute n^(log_b a) = n^(log₂2) = n¹ = n. Since f(n) = Θ(n) matches this exactly, we are in Case 2, which gives T(n) = Θ(n log n). Both methods agree.

Best, average and worst case

Here is something that surprises people: merge sort does not care about the input order. Whether the array is sorted, reversed or random, it splits at the same midpoints and performs every merge. Only the number of comparisons inside each merge changes a little.

For n = 8 the worst-case formula gives 8·3 − 8 + 1 = 17, which is exactly what our example needed, so that particular input happens to be a worst case. Feed the simulator an already sorted array of 8, such as 1 to 8, and the count drops to 12, which is (8/2)·3.

That consistency is a big deal in practice. Quicksort is usually faster on average, but a bad pivot sequence pushes it to Θ(n²). Merge sort gives you a guarantee.

5. Space complexity

Merge sort is not in-place in its standard form.

  • Auxiliary array: Θ(n). Merging needs somewhere to hold the two halves while it writes back into A. A good implementation allocates one buffer of size n once and reuses it, instead of creating new lists in every call.
  • Recursion stack: Θ(log n). The depth of recursion is ⌈log₂n⌉, and each frame stores only a few indices.

Total extra space: Θ(n) + Θ(log n) = Θ(n). This is merge sort's main weakness compared to heapsort (Θ(1) extra) and quicksort (Θ(log n) stack on average). In-place merging algorithms do exist, but they are complicated and slow enough that they are rarely used.

6. Checking the theory against real measurements

Theory is nice, but I wanted to see the n log n curve with my own eyes. I wrote a Python implementation that counts every comparison (the code is linked at the end), ran it on random arrays from 1,000 to 64,000 elements, and ran insertion sort on the same inputs for contrast.

Three things stood out to me:

  1. Doubling n slightly more than doubles the work for merge sort (8,695 → 19,430 is ×2.23). That extra bit beyond ×2 is the log factor showing up. For insertion sort, doubling n roughly quadruples the work, as you would expect from Θ(n²).
  2. At n = 8,000, insertion sort needed about 172 times more comparisons. That gap only grows with n. I skipped insertion sort beyond 8,000 because it was getting slow to run.
  3. The ratio sits below 1 and slowly rises. This matches the average-case formula n·log₂n − 1.25n: the −1.25n term matters less and less as n grows, so the ratio approaches 1 from below. It was satisfying to see a textbook formula appear in my own data.

7. How merge sort compares with other sorts

It is also worth knowing that no comparison-based sort can beat Θ(n log n) in the worst case. A decision tree that distinguishes all n! orderings must have height at least log₂(n!), which is Θ(n log n). So merge sort is asymptotically optimal among comparison sorts.

8. Where merge sort shows up in real life

  • Python's sorted() and Java's Arrays.sort for objects use Timsort, a hybrid that finds already-sorted runs in the data and merges them using merge sort's merge step. It needs stability for the reason in Section 2.
  • Sorting data that does not fit in memory (external sorting). Databases sort huge tables by sorting chunks that fit in RAM, writing them to disk, and then merging the sorted chunks. Merging only needs to read each file sequentially, which is exactly what disks are good at.
  • Linked lists. Merge sort is the natural choice for sorting linked lists because merging only relinks pointers, so it needs no extra array and no random access.
  • Counting inversions. A small change to the merge step counts how many pairs are out of order in Θ(n log n). Whenever we take an element from the right half, every remaining element in the left half forms an inversion with it. This is used in ranking comparisons and recommendation systems.

9. Common mistakes worth watching for

  • Using < instead of <= in the merge. The output is still sorted, so tests with plain integers pass, but the sort silently becomes unstable. You only catch it by testing records with equal keys, which is why my test script includes a stability check.
  • Creating new lists in every recursive call. Writing left = merge_sort(a[:mid]) is easy to read, but it allocates new lists at every level. Allocating one shared buffer up front, as my implementation does, avoids that overhead.
  • Computing the midpoint as (l + r) / 2 in Java or C. For very large arrays, l + r can overflow a 32-bit integer. The safe version is l + (r - l) / 2. This exact bug sat in Java's standard library binary search for years before it was found in 2006.
  • Forgetting the leftover copy. If you stop when one side runs out, the remaining elements of the other side are lost.

10. Play it: Convoy

Reading a trace is one thing. Making the decisions yourself is better. Convoy is one of three missions in Umbra (umbra-daa.vercel.app), a browser game I built where you take the place of the algorithm.

You start with a scrambled line of numbered pods. On the way down you choose where each piece is cut. On the way back up, two sorted lanes face each other and you pick which front pod goes next, by clicking it or pressing the left or right arrow key. The recursion tree builds above the board as you go, and every piece turns solid once it is sorted.

Your moves are scored against par, which is the number of decisions merge sort itself makes. A wrong pick tells you why the algorithm would have chosen differently, and equal pods come with a note on why the left one goes first. There is also an Autopilot mode that steps through the whole sort with an explanation of each move and the matching pseudocode line highlighted, and you can type in your own numbers.

Each round uses a different kind of input: scrambled, nearly sorted, reversed, many duplicates and so on. A good experiment is to compare the comparison counts between them. The number of cuts and levels never changes; only the comparisons inside each merge do.

11. Summary

  • Merge sort splits the array in half, sorts each half recursively, and merges the sorted halves.
  • Merging two sorted lists of total size k takes at most k − 1 comparisons, in linear time.
  • The recurrence T(n) = 2T(n/2) + Θ(n) solves to Θ(n log n) in the best, average and worst case.
  • It needs Θ(n) extra space, which is its main cost.
  • It is stable, predictable and optimal among comparison sorts, which is why its merge step lives on inside Timsort, external sorting and database engines.

The pile of answer scripts was a small problem, but the same halving trick scales to millions of records. That is what I find most satisfying about this algorithm: a very simple step, repeated at the right structure, gives a guarantee that the obvious approach cannot.
