Twenty Questions for a Million Items: How Binary Search Really Works

Think of a number between 1 and 1,000,000. If I am allowed to ask "is it bigger or smaller than this?", I can always find your number in at most 20 guesses. Not 500,000. Twenty.

That is binary search, and it is probably the best return on effort in all of computer science: about ten lines of code that turn a search through a million items into twenty steps. It is also famously easy to get subtly wrong. In this post I explain how it works, trace it by hand, prove the running time, measure it on real data up to ten million elements, and go through the mistakes that have caught out professional programmers for decades.

1. The idea: throw away half, every time

Binary search needs one thing from its input: the data must be sorted. That single fact is what makes each comparison so powerful.

Look at the element in the middle of the range you are searching:

  • If it is the target, you are done.
  • If it is smaller than the target, then so is everything to its left, because the array is sorted. The whole left half can be discarded without looking at it.
  • If it is larger, the whole right half goes instead.

One comparison, and half of the remaining candidates are gone. Repeat on what is left until you either find the target or run out of candidates.

This strategy is called decrease and conquer. Unlike merge sort, which splits a problem into two halves and solves both, binary search splits it in two and only ever continues into one.

2. Pseudocode

BINARY-SEARCH(A, t)                  // A is sorted in ascending order
    lo = 0
    hi = length(A) - 1
    while lo <= hi:
        mid = floor((lo + hi) / 2)
        if A[mid] == t:
            return mid               // found
        if A[mid] < t:
            lo = mid + 1             // t can only be to the right
        else:
            hi = mid - 1             // t can only be to the left
    return NOT-FOUND

Three details carry all the correctness:

  • lo and hi are both inclusive. The candidates are exactly the indices from lo to hi. When lo > hi there are none left.
  • mid + 1 and mid - 1, never just mid. We have already looked at A[mid] and it was not the target, so it must leave the range. Forgetting the ± 1 is the classic way to write an infinite loop.
  • lo <= hi, not lo < hi. When one candidate is left, lo == hi, and it still has to be checked.

The invariant that holds every time the loop condition is tested is: if the target is in the array at all, its index is between lo and hi. Each iteration keeps that true while shrinking the range, so the loop must end with either the answer or an empty range.

4. Time complexity

Counting the halvings

After each failed probe, at most half of the candidates survive. Starting from n candidates, after k probes at most n / 2ᵏ remain. The search must stop once that drops below 1:

n / 2^k < 1    ⟹    k > log₂ n

So the worst case is ⌊log₂n⌋ + 1 probes. For n = 15 that is 3 + 1 = 4, which is exactly what both examples above needed.

As a recurrence

Each call does a constant amount of work and then continues on half the input:

T(n) = T(n/2) + c,      T(1) = c

Unrolling it: T(n) = c + c + … + c, once per halving, which gives c · (log₂n + 1) = Θ(log n).

The Master Theorem agrees. With a = 1, b = 2 and f(n) = Θ(1), we get n^(log_b a) = n⁰ = 1, which matches f(n). That is Case 2, so T(n) = Θ(log n).

Best, average and worst

The average is only about one probe better than the worst case. That looks odd until you picture the search as a tree: half of all elements sit on the bottom level, a quarter on the level above, and so on. Most targets are found late.

It cannot be beaten by comparisons

Any algorithm that searches by comparing must be able to end in n + 1 different ways (n positions, plus "not found"). A sequence of k yes/no answers can only distinguish 2ᵏ outcomes, so k must be at least ⌈log₂(n + 1)⌉. That number is equal to ⌊log₂n⌋ + 1, which is exactly what binary search achieves. It is optimal among comparison-based searches.

5. Space complexity

  • Iterative version: Θ(1). Three integers, lo, hi and mid, regardless of the size of the array.
  • Recursive version: Θ(log n). Each recursive call adds a stack frame, and the recursion goes log₂n deep. This is why the loop version is the one normally used.

Neither version copies the array.

6. Checking the theory against real measurements

I wrote a Python implementation that counts every probe and ran it on sorted arrays from one thousand to ten million elements. For each size it records the worst case and the average over 2,000 random successful searches. The linear search column is the expected (n + 1) / 2 comparisons for a hit.

What I took from this:

  1. The worst case matches the formula exactly, at every size. There is no hidden constant to worry about.
  2. Multiplying n by 10,000 added only 14 probes (from 10 to 24). Linear search went from 500 to 5,000,000.
  3. The measured average is almost exactly log₂n − 1. For a million elements log₂n is 19.93, and the measured average was 18.95.

At ten million elements, binary search is doing about 224,000 times less work than a scan. No amount of hardware makes up for that.

7. Binary search compared with other ways to search

The honest cost of binary search is the sorting. Sorting takes Θ(n log n), so for a single lookup on unsorted data a linear scan is faster. Binary search wins when you search the same data many times. It also does something a hash table cannot: because the data is ordered, it can answer "what is the nearest value?" and "how many values lie between x and y?".

8. Where it shows up in real life

  • Standard libraries. Python's bisect, C++'s std::lower_bound and Java's Arrays.binarySearch are all binary search.
  • Database indexes. A B-tree index is a tree of sorted pages; finding a key inside each page is a binary search.
  • git bisect. When a bug appeared somewhere in the last thousand commits, Git checks out the middle commit and asks whether it is good or bad. Ten answers later you have the exact commit that broke things. The "sorted array" here is the commit history, and the order is "before the bug" and "after the bug".
  • Searching on the answer. Many optimisation problems ask for "the smallest value x for which something is possible". If being possible for x means it is also possible for everything larger, you can binary search over x itself, even though there is no array anywhere.

9. Common mistakes worth watching for

Binary search has a reputation: the idea was published in 1946, but according to Knuth the first version that was correct for all array sizes did not appear until 1962.

  • Integer overflow in the midpoint. In languages with fixed-size integers, (lo + hi) / 2 overflows when lo + hi exceeds the largest integer. The safe form is lo + (hi - lo) / 2. This exact bug sat in Java's standard library for about nine years before it was reported in 2006.
  • Writing lo = mid instead of lo = mid + 1. When lo and hi are next to each other, mid equals lo, nothing changes, and the loop never ends.
  • Using lo < hi as the loop condition with inclusive bounds. The last remaining candidate is never checked, so searching for the final element fails.
  • Running it on unsorted data. Nothing crashes. It simply returns wrong answers, which is worse.
  • Assuming it returns the first match. With duplicates, plain binary search returns some matching index. If you need the first one, you need the lower-bound variant, which keeps searching left after a match.

My test script checks the implementation against Python's bisect module for every possible target on arrays of every size from 0 to 59, which covers each of these edge cases, including empty arrays and absent values.

10. Play it: Signal Lock

To make the halving something you can feel, I built Signal Lock, one of three missions in  (umbra-daa.vercel.app), a browser game where you take the place of the algorithm.

A beacon is hidden in a sorted row of face-down sectors. Every ping costs one probe, and par is ⌊log₂n⌋ + 1. Ping wherever you like: the game dims everything your ping ruled out, and if you did not choose the middle, it tells you how many candidates your choice risked leaving compared with the middle. About one round in five, the beacon is not there at all, and you have to prove it.

Try pinging one sector at a time from the left on a 31-sector row. You will run out of par after five pings with most of the row still dark. Then play it again from the middle. That difference is Θ(n) against Θ(log n).

11. Summary

  • Binary search works on sorted data by checking the middle element and discarding the half that cannot contain the target.
  • It needs at most ⌊log₂n⌋ + 1 probes, so its running time is Θ(log n), and no comparison-based search can do better.
  • The iterative version uses Θ(1) extra space.
  • It can prove a value is absent just as quickly as it can find one.
  • It is simple to describe and easy to get wrong: watch the midpoint, the ± 1, and the loop condition.

Twenty questions for a million items, and twenty-four for ten million. That is what a logarithm buys you.
