Closest First: How Dijkstra's Algorithm Finds the Shortest Route

Every time a maps app gives you a route, or a packet finds its way across the internet, something has answered the same question: out of all the possible ways to get from here to there, which one costs the least?

Trying every route is hopeless. Even a small road network has more possible paths than you could ever list. In 1956 Edsger Dijkstra worked out a method that avoids all of that with one simple rule: always deal with the closest place you have not finished yet. He later said he designed it in about twenty minutes, without pen and paper, sitting at a café.

In this post I explain that rule, trace the algorithm by hand on a small graph, show why the greedy choice is safe, work out its running time for two different implementations, and then measure both to see whether the theory holds up.

1. The problem

We are given a weighted graph: a set of nodes (places) joined by edges (roads), where each edge has a weight (distance, time, fuel, cost). We pick one node as the source. The goal is the single-source shortest path problem: find the cheapest total weight from the source to every other node.

Dijkstra's algorithm solves this with one condition: no edge may have a negative weight. Section 6 shows what breaks if one does.

2. The idea: settle the closest node, then update its neighbours

The algorithm keeps a number for every node, dist[v]: the cheapest route to v found so far. At the start that is 0 for the source and ∞ for everything else, because no routes are known yet.

Then it repeats two steps:

  1. Settle. Among the nodes that are not finished, pick the one with the smallest dist. Its distance is now final.
  2. Relax. For each neighbour v of that node u, check whether going through u gives a cheaper route: if dist[u] + w(u, v) < dist[v], lower dist[v] to that value and remember that v's best route now comes through u.

That is the whole algorithm. It is greedy: at every step it makes the choice that looks best right now (the closest unsettled node) and never goes back on it. Greedy strategies often give wrong answers. Section 5 explains why this one does not.

3. Pseudocode

DIJKSTRA(G, s)
    for each node v in G:
        dist[v] = ∞
        prev[v] = NONE
    dist[s] = 0
    Q = all nodes in G                      // the unsettled nodes
 
    while Q is not empty:
        u = node in Q with the smallest dist     // settle
        remove u from Q
        for each edge (u, v) with v still in Q:  // relax
            if dist[u] + w(u, v) < dist[v]:
                dist[v] = dist[u] + w(u, v)
                prev[v] = u
    return dist, prev

prev is what turns a table of distances into actual routes. To read off the shortest path to any node, start there and follow prev backwards until you reach the source.

The table shows dist for every node after each step. A value in bold has just improved. Once a node has been settled, its value never changes again.

Three things in this trace are worth slowing down for.

Step 1 picks C, not B. After relaxing A's edges, B is at 4 and C is at 2. C is closer, so C is settled next, even though B was discovered first. Dijkstra orders nodes by distance, not by when they were found.

Step 2 changes its mind about B. The direct edge A–B costs 4. But going A → C → B costs 2 + 1 = 3. This is the moment that shows why the first route you find to a node is not necessarily the best one, and why dist values are only tentative until a node is settled.

The final answer is a tree. Following prev back from F gives F ← E ← D ← B ← C ← A, so the shortest route is A → C → B → D → E → F with total cost 2 + 1 + 5 + 2 + 3 = 13. The direct-looking route A → B → D → F costs 4 + 5 + 6 = 15. The prev links for all nodes together form the shortest-path tree shown in green.

5. Why the greedy choice is safe

The claim is: when a node u is picked as the closest unsettled node, dist[u] is already its true shortest distance.

Suppose it was not, and some cheaper route to u existed. That route starts at the source (settled) and ends at u (unsettled), so somewhere along it there is a first node, call it y, that is not settled yet. The part of the route up to y only uses settled nodes, so dist[y] already reflects it. And since u was chosen as the closest unsettled node, dist[y] ≥ dist[u].

The rest of the route, from y on to u, can only add to the cost, because no edge is negative. So the supposedly cheaper route costs at least dist[y], which is at least dist[u]. It is not cheaper after all. That contradiction proves the claim.

This is the same reasoning as: "every place I have not finished is at least this far away, and distances only grow, so nothing can come back and undercut the closest one."

6. What goes wrong with a negative edge

The proof leans entirely on "the rest of the route can only add to the cost". Take that away and the algorithm fails.

Edges:   A → B  cost 2
         A → C  cost 5
         C → B  cost −4

From A, Dijkstra sees B at 2 and C at 5. B is closest, so B is settled at 2 and never looked at again. But A → C → B costs 5 + (−4) = 1, which is better. The algorithm reports 2 and is wrong.

For graphs that can have negative edges, the Bellman–Ford algorithm is the correct tool. It is slower, at Θ(V · E), but it does not assume that settled means final.

7. Time complexity

Let V be the number of nodes and E the number of edges. The algorithm does two kinds of work:

  • V "settle" operations, each finding and removing the closest unsettled node.
  • At most E "relax" operations, each possibly lowering one distance. Every edge is looked at once from each end.

How long these take depends entirely on how the unsettled nodes are stored.

Array version. Each of the V settle steps scans all V nodes, giving V² in total. The E relaxations are Θ(1) each and are absorbed, since E is at most V².

Binary heap version. V removals cost log V each, and up to E distance updates cost log V each, giving (V + E) log V.

Which is better depends on the graph:

  • For a sparse graph, where E is close to V (road networks, for example), the heap gives roughly V log V against V². The heap wins easily.
  • For a dense graph, where E is close to V², the heap version becomes V² log V, which is worse than the simple array. More sophisticated is not always faster.

8. Space complexity

  • Graph storage: Θ(V + E) as an adjacency list.
  • dist and prev: Θ(V).
  • Priority queue: Θ(V) for an indexed heap. The common "lazy" version, which pushes a new entry instead of updating an old one, can hold up to Θ(E) entries.

Total: Θ(V + E).

9. Checking the theory against real measurements

I implemented both the array version and the min-heap version in Python, checked that they agree on 200 random graphs, and then timed them on connected sparse graphs with E = 4V.

Figure 2: On a log–log plot the array version climbs with a slope of about 2 and the heap version with a slope of about 1.

The exact milliseconds depend on my laptop and change a little between runs, but the pattern is stable:

  1. Doubling V roughly quadruples the array version (7.7 → 33.0 → 149.7 → 599.1). That is Θ(V²) showing itself.
  2. Doubling V a little more than doubles the heap version (0.6 → 1.4 → 2.9 → 7.0), as V log V predicts.
  3. The gap keeps widening, from about 12× to about 86×. That is what different growth rates mean in practice: the advantage is not a fixed factor, it grows with the input.

10. How Dijkstra relates to other algorithms

It is also a close relative of Prim's algorithm for minimum spanning trees. The code is almost identical; the only difference is that Prim compares the weight of a single edge, while Dijkstra compares the total distance from the source.

11. Where it is used

  • Internet routing. OSPF, one of the main protocols routers use inside a network, has every router run Dijkstra's algorithm on its map of the network to build its routing table.
  • Maps and navigation. Route planners are built on Dijkstra's idea, with heavy preprocessing and heuristics such as A* layered on top so that continent-sized road networks can be searched in milliseconds.
  • Games. Pathfinding for characters on a map is usually A*, which is Dijkstra with a sense of direction.
  • Anything that can be drawn as a weighted graph: cheapest flight connections, task scheduling, even currency conversions.

12. Common mistakes worth watching for

  • Treating a node as finished when it is first discovered. A distance is only final when the node is settled. In the example, B was first seen at 4 and finished at 3.
  • Using it with negative weights. It will run happily and give wrong answers.
  • Forgetting to skip stale heap entries. The lazy heap version leaves old entries behind. Without the check if d > dist[u]: continue, nodes are processed more than once and the running time degrades.
  • Returning only the distance. Without prev you know how far, but not which way.
  • Stopping too early or too late. If you only need one destination, you can stop as soon as it is settled. Stopping when it is first reached is wrong.

13. Play it: Starlane

The settle-then-relax rhythm is much easier to absorb by doing it. Starlane is one of three missions in Umbra (umbra-daa.vercel.app), a browser game I built where you take the place of the algorithm.

Each round generates a fresh star map: six to eight stars, jump lanes with fuel costs, and a random home star. Every turn you click the star Dijkstra would settle next. Pick correctly and you watch each of its lanes get relaxed. Pick wrong and you are told why: that star is already settled, or has not been reached yet, or another one is closer.

Par is simply the number of stars, because the algorithm makes exactly one greedy decision per node. If you finish on par, you have executed Dijkstra's algorithm by hand without a single wrong turn.

14. Summary

  • Dijkstra's algorithm finds the cheapest route from one source to every node in a graph with non-negative edge weights.
  • It repeats two steps: settle the closest unsettled node, then relax its edges.
  • The greedy choice is safe because any other route to that node has to pass through something at least as far away, and weights cannot be negative.
  • It runs in Θ(V²) with an array and Θ((V + E) log V) with a binary heap, using Θ(V + E) space.
  • For negative weights, use Bellman–Ford. For unweighted graphs, BFS is enough.

One rule, closest first, applied patiently until nothing is left. It is hard to think of another twenty minutes at a café that paid off this well.
